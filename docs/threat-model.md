# Threat model (v1.0, with contracts v1.0)

Scope: the MVP described in `decisions.md` (confirmed v1.0) and `contracts/` v1.0.
Status: **design only — nothing below is implemented or tested yet.** Each mitigation names the contract element
that makes it possible; whether the implementation actually does it must be proven by the tests in `test-plan.md`.

## Assets

| Asset | Where it lives |
|---|---|
| Ballot secrecy (who chose whom) | split: voter ↔ token (credential DB), nullifier ↔ sealed ballot (ballot DB), election private key (commission) |
| Eligibility (one person, one vote) | token states, nullifier registry |
| Integrity of roster, ballots, results | Core DB + ledger anchors + checkpoints |
| Audit trail | ledger events, rejections, rejected_attempts, findings, reports |

## Actors

Voter · Election commission admin (Core operator) · Approver of each organization · Ledger operator (Gateway + nodes)
· Rule Engine / Audit Agent services · External AI API provider · Outside attacker.

## Threats and mitigations

| # | Threat | Mitigation (contract element) | Residual risk / limit to state in the report |
|---|---|---|---|
| S1 | Link voter to ballot by **time** (redeem time ≈ ballot time) | bucketed time on voter events, random `evr_` IDs, no `received_at`/`seq` on voter events, shuffled per-bucket release, views use checkpoint numbers whose interval is an integer multiple of the bucket (never finer), bucket size rule of D-10 (≥ 10 expected voters per bucket, enforced at roster freeze) | **If a bucket contains only one or two voters, its TOKEN_USED and BALLOT_RECEIVED pair up; anyone holding the CSV / credential DB can then attribute those ballots, and after the private key is revealed (D-23) read the choice.** With 100 voters, 60 s buckets and a 2 h window most ballots would be attributable — hence the D-10 sizing rule. Service logs keep exact request times but no identifiers. The sizing rule assumes full turnout and an even spread; real turnout below 100 %, or voting concentrated in a few buckets, leaves fewer voters per bucket. If all voters of one checkpoint choose the same candidate, the revealed key plus participation data reveals that choice for each of them |
| S2 | Link voter to ballot by **stored data** | no column or view joins token and nullifier; credential generated in browser; only hashes stored; Rule Engine / AI / auditors have no DB access (D-06, D-07) | Redeem writes the token update and the nullifier insert in **one DB transaction**, so a DB superuser or anyone with WAL / transaction-metadata access (xmin, commit order, WAL position) can link them **without code changes**; a Core operator can also link them in memory. Voter-side rows store only bucket/checkpoint values and random keys (contracts README), but physical insertion order and WAL remain visible to DB administrators. Unlinkability holds only against parties without DB-admin access. Alternatives: D-06 (A) two instances / (C) blind signatures |
| S3 | Commission reconstructs votes | S1 + S2 remove the links visible to view, ledger and log readers | **Ballot secrecy is not guaranteed against the election commission**: it operates Core and its database (S2: token ↔ nullifier linkable via DB internals or in memory) and holds the private key (D-23), so it can link voters to choices even before the tally. Threshold decryption / blind signatures are future work |
| S4 | Proxy voting by whoever holds raw links | links only in CSV/email at issue time (D-16); CSV kept encrypted in memory for 15 min for retries, then wiped | Admin who exported the CSV can vote for others; **not prevented in MVP** |
| S6 | Vote-buying / coercion | key revealed only to Rule Engine, staff and auditors (not the public, not the AI) | **Not receipt-free:** sealed boxes are not re-randomised, so a voter using a modified client can keep the ephemeral secret, or submit a ciphertext prepared by a buyer and show its receipt on the public receipt API; after the key reveal, saved sealed bytes also prove the choice. Coercion resistance must not be claimed |
| S7 | Linking a reissued or newly added voter to their vote | none beyond bucketing | When only one or two tokens are issued in a batch (TOKEN_REISSUE, ROSTER_AMEND add), TOKEN_REVOKED.voter_key + the new token_status row + its TOKEN_USED bucket reveal whether and in which bucket that voter voted (participation and time, not the choice) |
| S8 | Revoked token not actually belonging to the target voter | R4 compares voter_keys, not token ownership | R4 cannot verify that a revoked token_hash belongs to the stated voter_key (no such mapping is exposed, by design) |
| S5 | Participation (who voted, not for whom) | none | Holders of the CSV / credential DB can see which tokens were used, i.e. who voted (as in many real elections). Not hidden in the MVP |
| E1 | Double vote via reused link | redeem is atomic; USED tokens can never be re-enabled (D-09); Gateway DUPLICATE_CONTENT; R1 | — |
| E2 | Double vote via hidden credential + "lost credential" claim, or redeem during a pending TOKEN_REISSUE | no reactivation exists; TOKEN_REISSUE only for UNUSED tokens, re-checked atomically at execution (row lock); Gateway rejects TOKEN_REVOKED for used tokens; R1 `used_then_revoked` | Lost credential after redeem = abstention (usability cost) |
| E3 | Concurrent identical ballots | nullifier unique constraint; identical retry returns original receipt | — |
| I1 | Admin changes roster after freeze, or forges multi-org approval | ROSTER_AMEND needs signatures of other orgs; signer keys come only from the on-chain organization registry written by each org's own node account (hashing.md); threshold ≥ 2 and ≤ orgs − 1; contract refuses unapproved ROSTER_AMENDED; R4 target / roster-chain checks; R5 snapshots | Whoever controls an org's node account and key *is* that org: if one person runs all nodes and keys (typical demo, D-21), approvals are not independent |
| I2 | Ballot row or sealed ballot bytes modified / deleted in DB | snapshots include `sealed_ballot`; R5 checks `H(sealed_ballot) = ballot_hash` and snapshot hashes; tally recomputes the hash before decrypting | R5 re-checks every committed checkpoint and matches each ballot row with its ledger event, so later changes to committed rows are caught. Changes made inside the open checkpoint before it is committed are hashed into that checkpoint; they are caught only if they break the row-to-ledger match (e.g. a new ballot without an accepted BALLOT_RECEIVED) |
| I3 | Late ballots accepted | Core refuses after close (stricter-first); Gateway rejects bucket after end; contract rejects batch range after end; R2 | Per-event check is Gateway software, not the contract (D-22) |
| I4 | Gateway / ledger operator alters stored events | leaf hash covers the whole event; anchors on chain; `/anchors/{id}/leaves` + `anchorAt` read from the pinned node (chain-interface.md) allow independent recomputation | Validator nodes run in one Docker host are not independent organizations (D-03) |
| I5 | Result changed after tally | TALLY_PUBLISHED once only, ELECTION_FINALIZED binds result_hash, nothing after FINALIZED | — |
| I6 | Tally misreported or ballots dropped at tally (by the key holder) | final_checkpoint must equal the CLOSE_FINAL checkpoint (contract + R3/R5); ballot_set_root over all accepted ballots ≤ final checkpoint (recomputable from the ledger); excluded / invalid counts and invalid hashes in TALLY_PUBLISHED; private key revealed after tally so R5 re-decrypts and recomputes results | Before the key is revealed, the key holder can read ballots early; a misreport is detected only after tally, before finalization |
| I9 | Commission makes another organization the operator (to get its own reviews counted) | operator_org comes from the on-chain registry, effective only after every organization confirmed it; it is in config_hash and in electionState; never from a staff login | — (same key-control caveat as D-21) |
| I10 | Core censors organizations' reviews or approvals | organizations can submit decisions and reviews directly to the contract (chain-interface.md); the Gateway indexes them | An organization unaware of the direct path may still rely on Core. Opening a proposal has no direct chain path (only the Gateway may call openProposal, relayed by Core), so the operator can refuse to open another organization's request (e.g. a VOID) |
| I11 | Rule Engine or Gateway operator forges, alters or suppresses finding records | finding records are signed by the Rule Engine key registered on chain (confirmed by all orgs) and verified by the contract; the Rule Engine can submit directly on chain; finding_checkpoint ≤ last committed; finalize requires R1–R5 records for the TALLY checkpoint and a stored body for every record; every participating organization (and invited auditors) can re-run the rules with staff view access (`/v1/elections/{id}/views/{view}`) plus a read-only Gateway `auditorKey` | The Rule Engine operator itself is trusted to run all rules honestly (D-25); a selective operator is detected only by an independent re-run. The Gateway operator (D-26) can delay relaying but not forge. An independent re-run can only **detect and publicise** a selective Rule Engine: other organizations cannot record findings (only ruleEngineSigner can) and cannot review PASS findings, so there is no contract-level way for them to block finalization on that basis |
| I12 | Gateway operator injects or pre-empts an unsigned Core system event (e.g. calls the once-only publishTally first), or calls the contract with arguments that differ from the ledger event | only the registered gatewayAccount (confirmed by all orgs) may call Gateway writes; Core compares every source-core ledger event with its outbox (event_id, payload_hash), alerts and stops the FIFO; R5 compares the contract's electionStateAtCheckpoint(k) and governance fields with the ledger events; Core checks the governance fields right after ELECTION_CREATED by reading a node not run by the Gateway operator (GOVERNANCE_MISMATCH: FIFO stays stopped, election abandoned and deleted at Core) | **Detected, not prevented**: Core system events are not signed by Core in the MVP; recovery is ELECTION_VOID (D-26). The Gateway account can still append unsigned events to an abandoned election ID on chain; they have no official meaning because no Core election exists |
| I13 | A registered organization that does not take part in the election approves or reviews, or the Gateway registers other organizations / another threshold on chain | the contract, Core, R4 and the finalize quorum count only organizations in the election's organizations; Core (before freezing, from a node) and R5 (every checkpoint, from a node) compare the contract's governance fields with ELECTION_CREATED | A Gateway that calls finalizeElection itself while the governance check is failing could still finalize; Core alerts but cannot undo a FINALIZED state; the checks are independent only if the contract address and at least one node URL are pinned in the deployment configuration (confirmed by all organizations), not taken from the Gateway |
| I7 | Commission clears audit findings about itself and finalizes | findings registered at the Gateway by the Rule Engine (FINDING_RECORDED); reviews signed per organization and recorded on chain (FINDING_REVIEWED); operator_org reviews never count; contract checks review quorum at ELECTION_FINALIZED | Independence again depends on separate people holding the other organizations' keys (D-21) |
| V1 | One organization blocks finalization | any organization's signed CONFIRMED_ISSUE review makes the finding CONFIRMED_ISSUE, which blocks finalize; the only exit is a multi-org ELECTION_VOID | **Any single organization can veto finalization** (by design, to avoid silencing a real problem); an abusive veto forces a void and re-run |
| L2 | Governance stalls | none in the MVP | Liveness depends on the organizations: with 3 organizations and threshold 2, one absent non-operator organization means no FAIL can be RESOLVED and no admin action approved; after a CONFIRMED_ISSUE, ELECTION_VOID needs approvals from organizations other than the requester, so a non-cooperating set of organizations can leave the election TALLIED indefinitely |
| I8 | Approver or reviewer is shown misleading data by Core | approvers see `target_people` and can read the roster (`roster:read`); reviewers' clients must check Hc(finding body) against the ledger finding_hash before signing (hashing.md) | Approvers still trust Core's voter_key ↔ person mapping (the roster itself comes from Core). The admin and voter web clients are distributed by the operating organization; approvers and reviewers must use clients that recompute digests themselves (hashing.md obligations), otherwise a modified client could make them sign something else |
| A1 | AI writes or decides | agentKey can only read and create reports; reports cannot carry human_review; no tool executes actions | Prompt injection through log text can still mislead the explanation → evidence IDs are verified, human makes the decision |
| A2 | AI fabricates evidence | Core resolves every evidence ref before storing (EVIDENCE_NOT_FOUND) | References can exist but be irrelevant → human review |
| A3 | Data sent to external AI API | only PII-free views, no raw tokens/credentials, never the election private key (null for agentKey) | token/nullifier hashes, ballot hashes and encrypted sealed ballots reach the provider; acceptable only for synthetic test data |
| L1 | Gateway operator watches live traffic | voter events released per bucket and shuffled; Gateway must not record arrival time/order | A Gateway operator capturing traffic sees bucket-level batches only; anything finer depends on the Core release behaviour being implemented as specified |
| E4 | Core operator stuffs ballots for abstainers (marks unused tokens USED, registers nullifiers, casts ballots) | counts stay consistent, so R1–R5 cannot detect it; only voters checking that they did not vote, or turnout comparisons, would | **Not detectable in the MVP** — must not claim protection against an insider with Core write access |
| A4 | Core alters AI reports or their human_review afterwards | reports and human_review are stored only at Core (finding reviews, by contrast, are on chain) | AI reports are not tamper-evident; experiment results based on them must be exported and hashed at the end of each run |
| I14 | Operator admin resumes a stopped outbox alone (e.g. after an injected-event alert) | resume is logged as a core-api alert visible to all organizations | One operator admin can resume without other organizations' consent |
| O1 | Operator controls staff accounts and execution | staff and auditor accounts are created by the deployment's setup script and stored in Core (operator org); no account API in the MVP; an approved action is executed by Core | The operator can create or block staff accounts of other organizations in Core (their chain keys and direct submissions are unaffected) and can refuse to execute an approved action (e.g. a VOID); detected as `missing_effects` only after execution, not if it never executes |
| L3 | Rule Engine operator stops | none | Without new finding records for the TALLY checkpoint the election cannot be finalized; the only exit is ELECTION_VOID. A lost finding body (Rule Engine failed to keep it) likewise blocks finalization. A finding body whose hash does not match its record (Rule Engine bug) can never be stored, with the same consequence |
| R1 | Refused attempts disappear | Gateway rejections (anchored via `rejections_root`), Core `rejected_attempts` (hashed per checkpoint) | Refused attempts after the TALLY checkpoint (e.g. rejected finalize tries) are kept in `rejected_attempts` but are no longer hashed into any committed checkpoint |
| K1 | Organization key compromise or rotation | keys fixed per network in the registry | No key rotation procedure in the MVP; a compromised org key can approve/review as that org until the network is reset |
| D1 | Ledger unavailable during voting | outbox keeps accepting voter requests while OPEN; RETRY_LATER; the Rule Engine records alerts instead of findings until the ledger catches up | If the ledger is down at window_start the opening itself waits (OPEN is applied only after ACCEPTED), shortening the voting time; long outages delay audits and tally |

## Claims we must NOT make in the MVP

Complete anonymity against the operator or DB administrator · receipt-freeness or coercion resistance · prevention of proxy voting · detection of ballot stuffing by a Core insider · end-to-end verifiability ·
independent multi-organization operation (unless real separate operators hold the keys and nodes) ·
"the smart contract rejects each late ballot".
