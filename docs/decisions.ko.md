## 상세

### D-01. 2개월 구현 범위
- **추천안**
  - 구현: 단일 선택(후보 1명 선택) 투표 방식 하나로 선거 생성 → 명단 고정 → 링크 발급 → 투표권 등록 → 암호화 투표 → 원장 기록 → 체크포인트 → 규칙 R1~R5 → (FAIL/INCONCLUSIVE 시) 기관 서명 검토 → 개표·확정의 정상 경로 1개와 결함 주입 시나리오
  - 다른 투표 방식(복수 선택, 순위 투표)은 정상 경로 검증 후 확장 계획만 작성
  - 설계·향후 과제로만 설명: 블라인드 서명, 임계값 복호화, Isolation Forest 비교군, 대규모 반복 통계 실험
- **영향**: 전체 일정, `docs/test-plan.md`
- **확정 보완(v1.0)**: AI 보고서는 선택 기능(system-design 9장). 필수 결함 시험은 T01·T02·T04·T05·T08·T15이고, 나머지는 선택.

### D-02. 블록체인 플랫폼
- **선택지**: (A) Hyperledger Besu(QBFT) + Solidity, (B) Hyperledger Fabric, (C) 기존 PureVoting private 체인 재사용
- **추천안**: (A). Harits가 기존 체인을 바로 다룰 수 있다면 (C)도 가능
- **영향**: `Signature.scheme`(Besu면 `eip191-secp256k1`), Gateway API는 플랫폼과 무관

### D-03. 노드 수·운영 주체
- **배경**: QBFT 계열은 노드 3개면 1개 고장에도 합의가 멈춤(3f+1)
- **추천안**: 검증 노드 4개. 단, Docker로 여러 노드를 띄운 것은 **독립 기관이 운영한다는 증거가 아님**을 보고서에 명시
- **영향**: `GET /v1/nodes`, 시연 시나리오, `docs/threat-model.md`
- **확정 보완(v1.0)**: 플랫폼과 무관한 부분만 확정. ① 검증 노드는 참여 기관들이 나눠 운영하는 것으로 가정하고, Docker 다중 노드가 독립 기관 운영의 증거가 아님을 보고서에 적는다. ② Gateway 운영 기관이 아닌 기관(시연: 참관인)이 운영하는 노드 1개 이상을 고정 노드로 배포 설정에 둔다(chain-interface.md). 노드 수는 D-02에 따라 Harits가 정한다(BFT 계열이면 4개).

### D-04. 원장 기록 단위
- **추천안**
  - 시스템 이벤트(선거 상태, 명단, 승인, 체크포인트 등)는 즉시 체인에 기록
  - 투표 쪽 이벤트(TOKEN_USED, BALLOT_RECEIVED)는 순서를 섞은 배치로 묶어 **머클 루트만** 기록. 배치 주기 60초 또는 50건
  - 그래서 체인(스마트 계약)은 개별 투표 이벤트를 볼 수 없고, 배치의 시간 범위만 검사함(D-22)
- **영향**: `ledger-events.schema.json`, `/v1/anchors`
- **확정 보완(v1.0)**: '즉시'는 Gateway가 받은 시스템 이벤트를 배치 없이 개별(또는 소규모 묶음)로 앵커한다는 뜻이며, Core는 시스템 이벤트를 시간 구간 끝에 보낸다(contracts README 'Delivery order'). 배치 주기 60초(= README의 batch interval)·최대 50건은 플랫폼과 무관하게 확정한다.

- **확정 보완(v1.0)**: 스마트 계약 언어는 D-02 결정을 따른다(Besu면 Solidity, Fabric이면 chain-interface.md와 같은 함수명·인자의 체인코드).

### D-06. DB (v0.3 변경)
- **배경**: v0.2는 "DB 2개를 한 트랜잭션으로" 처리한다고 써서 PostgreSQL에서 구현할 수 없는 모순이 있었음(감독관 P1-2)
- **추천안**: PostgreSQL **데이터베이스 1개**에 스키마 `credential`(선거·명단·토큰 해시·관리자 작업)과 `ballot`(투표권 해시·암호화 투표·영수증)을 두고 서로 다른 DB 권한으로 소유. 두 스키마 사이에 공통 키 없음. 링크 사용 처리와 투표권 등록은 한 트랜잭션
- **공개해야 할 한계**: DB 최고 관리자나 WAL·트랜잭션 메타데이터에 접근할 수 있는 사람은 코드 변경 없이도 토큰과 투표권을 연결할 수 있음. 비연결성 보장은 DB 관리 권한이 없는 쪽(규칙 엔진·AI·원장·감사자)에 대해서만 성립
- **다른 선택지(팀장 결정)**
  - (A) DB 인스턴스 2개 + 비원자 2단계 처리: 연결 위험은 줄지만 중간 장애 시 토큰만 사용되고 투표권이 등록되지 않을 수 있어 R3 보정 규칙이 필요
  - (B) 위 추천안(원자 처리 + 한계 공개)
  - (C) 블라인드 서명: 운영자에 대해서도 비연결, 일정 위험 큼
- **영향**: Core API 설명, `docs/threat-model.md` S2

### D-07. 익명 투표권 방식 (v0.2 변경)
- **추천안**
  1. 웹이 URL fragment(`#t=...`)에서 토큰을 읽음
  2. **브라우저가 무작위 투표권을 만들어 먼저 자기 저장소에 보관**한 뒤 `nullifier_hash = H(투표권)`만 서버에 보냄
  3. 서버는 한 트랜잭션에서 토큰 확인 → 사용 처리 → ballot_db에 nullifier_hash 등록. 토큰과 nullifier의 연결은 저장하지 않음
  4. 투표할 때 투표권 원문을 함께 보내고, 서버는 해시가 등록돼 있고 미사용인지 확인
- **이점**: 응답이 유실돼도 브라우저에 투표권이 남아 있어 재시도가 안전함. 서버는 투표권 원문을 저장하지 않음
- **한계(문서에 명시)**: 서버 운영자가 요청 처리 중 메모리를 조작하면 토큰과 nullifier를 연결할 수 있음 → 블라인드 서명은 향후 과제
- **영향**: `POST /v1/credentials:redeem`, `POST /v1/ballots`

- **추천안**: 선거 키 쌍 생성, 웹에서 공개키로 봉인, 마감 후 개표 때만 개인키 사용(D-23)

### D-09. 링크·투표권 분실 시 정책 (v0.2 변경)
- **배경**: v0.1의 "사용된 링크 재활성화"는 유권자가 투표권을 숨겨 두고 분실을 주장하면 **두 번 투표할 수 있고 R3로도 잡히지 않는 결함**이 있었음(감독관 P0-2)
- **추천안**
  - 사용된 링크는 어떤 경우에도 다시 쓸 수 없음(재활성화 작업 자체를 없앰)
  - **미사용** 링크를 잃어버린 경우만 `TOKEN_REISSUE`(승인 필요): 기존 토큰 폐기(TOKEN_REVOKED) 후 새 링크 발급
  - 링크를 사용한 뒤 투표권을 잃어버린 경우(브라우저 저장소 삭제 등)는 기권 처리
- **다른 선택지**: 투표권을 토큰에서 HMAC으로 유도 → 재발급해도 nullifier가 같아 이중 투표는 막히지만 서버 비밀 보유자가 연결 가능
- **영향**: `AdminActionType`, R1·R4
- **확정 보완(v1.0)**: TOKEN_REISSUE는 선택 기능(system-design 9장)이다. 구현하지 않으면 미사용 링크를 잃어버린 경우도 기권으로 처리한다.

### D-10. 투표 쪽 시각 정밀도 (v0.2 변경)
- **배경**: v0.1은 수신 시각·ULID ID·정렬 순서로 정밀 시각이 새어 나가는 결함이 있었음(감독관 P0-1)
- **추천안**
  - 투표 쪽 이벤트: 시각은 구간(크기는 아래 기준)으로 내림, ID는 시각 없는 무작위 `evr_`, 수신 시각과 순번은 기록하지 않음
  - view에는 시각 대신 체크포인트 번호만 둠
  - 투표 시작·마감 시각은 구간 경계에 맞춤 → R2가 `occurred_at + 구간 > 마감`으로 마감 후 접수를 정확히 판정
- **트레이드오프**: 구간이 클수록 익명성은 좋아지고 시각 해상도는 낮아짐
- **강제(v0.7)**: 명단 고정 시 `명단 수 × 구간 ÷ 투표 기간 < 10`이면 거부(BUCKET_TOO_SMALL). 기본값은 두지 않음
- **크기 기준(v0.6)**: 한 구간에 평균 10명 이상이 투표하도록 정함(대략 `구간 ≥ 10 × 투표 기간 ÷ 예상 투표자 수`). 예: 100명·2시간이면 구간 15분 이상. 구간당 투표자가 1~2명이면 링크 사용과 투표 접수가 짝지어져, 개표 후 키 공개와 합치면 CSV·자격 DB 보유자가 표의 주인을 알아낼 수 있음(위협 모델 S1)
- **영향**: `ledger-events.schema.json`, `ElectionCreate.time_bucket_seconds`

### D-11. 승인 대상·기준·서명 (v0.2 변경)

| 작업 | 승인 기준 |
|---|---|
| `ROSTER_AMEND` (명단 고정 후 정정) | 요청 기관 외 2개 기관 |
| `TOKEN_REISSUE` (미사용 링크 재발급) | 요청 기관 외 2개 기관 |

- 요청 기관도 요청에 서명하고, 승인·거절도 각 기관이 **자기 키로 서명**함. Core와 Gateway는 서명을 전달만 함

- 서명 검증은 어떤 플랫폼에서도 체인(스마트 계약 또는 체인코드)이 한다. Gateway 검증으로 대체하면 D-26과 위협 모델 I1·I7·I11의 주장이 성립하지 않으므로, 그 경우 contracts와 위협 모델을 먼저 고쳐야 한다(v1.0). **이것은 D-02 플랫폼 선택의 필수 조건**이다
- 업무 승인(기관 서명)과 블록체인 합의(노드)는 다른 것으로 구분해서 설명
- **영향**: `contracts/hashing.md`, `/v1/proposals`, R4
- **확정 보완(v1.0)**: '2개 기관'은 승인 임계값(2 ≤ 임계값 ≤ 참여 기관 수−1, 시연 2)이다. 필수 구현은 ROSTER_AMEND·ELECTION_VOID이고 나머지는 선택(system-design 9장).

### D-12. Core ↔ 원장 일관성 (v0.2 변경)
- **추천안**
  - Core DB 변경과 outbox 기록을 한 트랜잭션으로 하고, 워커가 같은 event_id로 재시도
  - 시스템 이벤트는 선거별 순번(seq)으로 순서 보장, 투표 이벤트는 순번 없음(순서 노출 방지)

### D-24. 확정(finalize) 조건 (신규)
- **배경**: v0.2는 확정 조건이 AI 보고서의 사람 검토에 묶여 있어 AI 없이(규칙만 비교군) 확정할 수 없었음(감독관 P1-9)
- **배경(v0.4)**: v0.3은 선관위가 자기 행위에 대한 FAIL을 혼자 기각하고 확정할 수 있었고, 검토 기록이 원장에 남지 않았음(감독관 3차 P1-2)
- **추천안**
  - 규칙 엔진이 finding 해시를 Gateway에 직접 기록(FINDING_RECORDED). Core는 finding을 숨기거나 바꿀 수 없음
  - FAIL/INCONCLUSIVE 검토는 각 기관이 자기 키로 서명해 원장에 기록(FINDING_REVIEWED). **운영 기관(선관위) 외 기관** 서명이 임계값 이상이면 해결(RESOLVED), 하나라도 실제 문제(CONFIRMED_ISSUE)면 확정 불가
  - 장애로 생긴 INCONCLUSIVE는 같은 규칙의 이후 PASS로 자동 대체(SUPERSEDED). FAIL은 대체되지 않음
  - Core가 finding 본문을 받는 조건은 "스키마 유효 + 해시 일치" 하나뿐(v0.13). 증거 참조가 확인되지 않아도 거부하지 않고 경고로 표시. 규칙 엔진은 기록 전에 스키마를 미리 검증
  - 원장 기록은 있는데 Core에 본문이 아직 없으면 규칙 엔진이 같은 본문을 나중에 다시 올림(Core는 색인 전이면 503으로 재시도 요청). 규칙 엔진은 확정·무효 전까지 본문을 보관(v0.12)
  - 스마트 계약이 확정 시점에 이 조건을 원장 기록으로 다시 확인. AI 보고서는 검토 참고용(선택)
- **실제 문제 확인 시(v0.5)**: 확정 불가. 유일한 출구는 다기관 승인을 받은 `ELECTION_VOID`(무효, 종료 상태). 재선거는 새 선거로 진행
- **다른 선택지**: 현행(직원 검토만) 유지 + 한계 공개 → 일정은 안전하지만 "다기관 감사" 주장 불가
- **영향**: Gateway `/v1/finding-records`, `PATCH /v1/findings/{id}/review`, `POST /v1/elections/{id}:finalize`

### D-25. 규칙 엔진 운영 주체 (신규)
- **배경**: 규칙 엔진 키를 가진 쪽은 finding을 선별해 등록하거나(PASS만 등록) 감사를 늦출 수 있음(감독관 4차 P2)
- **추천안**: ruleKey는 선관위가 아닌 중립 기관이 보관·운영. 각 참여 기관(과 초청 감사자)이 직원 view와 Gateway 읽기 전용 키(auditorKey)로 같은 데이터에 규칙을 다시 돌려 결과를 비교할 수 있게 규칙 엔진 코드를 공개
- **한계**: MVP 시연에서 한 사람이 운영하면 "독립 감사"가 아님을 명시
- **확정 보완(v1.0)**: 시연에서 중립 기관이 Gateway·규칙 엔진·AI를 함께 운영하므로 권한이 한 기관에 모인다는 점을 한계로 적는다.

### D-26. Gateway 운영 주체 (신규)
- **배경**: Gateway 운영자는 원장 기록을 전달하는 위치에 있음(감독관 5차 P1-2)
- **추천안**: 선관위가 아닌 중립 기관이 운영. Gateway 계정은 운영 기관 노드가 레지스트리에 등록하고 모든 기관이 확인해야 유효(v0.10). 계약상 승인·검토·finding 기록은 모두 서명자가 서명하고 스마트 계약이 검증하므로 Gateway 운영자는 위조할 수 없음. 전달을 막거나 늦추면 서명자가 체인에 직접 제출(chain-interface.md)
- **한계**: 시연에서 한 사람이 Gateway와 노드를 모두 운영하면 독립성이 없음을 명시. Gateway가 계약에 넘긴 선거 생성 인자(참여 기관·임계값 등)는 Core가 생성 직후(Gateway 운영 기관이 아닌 노드를 직접 조회), R5가 매 체크포인트마다 원장 기록과 대조함. 불일치하면 선거를 폐기(Core에서 삭제)함(v0.16). 계약 주소와 Gateway 운영 기관이 아닌 노드 URL은 모든 기관이 확인한 배포 설정값으로 고정하고, Gateway가 알려 주는 값은 대조용으로만 씀(v0.17). Core의 시스템 이벤트는 Core 서명이 없어 Gateway 운영자가 끼워 넣거나 먼저 호출할 수 있음 — Core가 outbox와 대조해 탐지하지만 막지는 못함(v0.8, 위협 모델 I12). Core 서명 추가는 향후 과제
- **확정 보완(v1.0)**: 시연 배치: Gateway 운영 = 중립 기관, 고정 노드 = 참관인(Gateway 운영 기관이 아닌 기관) 노드. Core와 규칙 엔진 모두 이 노드를 읽는다.
